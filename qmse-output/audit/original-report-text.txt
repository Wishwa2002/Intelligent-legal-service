1. Introduction

[13] p
1.1 Purpose of this report

[14] p
This report documents the planned, tool-based testing of the LegalEase AI platform that the group built for SE3090 Assignment 1. It follows the SE3110 specification: it states what was tested and why, records the test cases with expected and actual results, lists the defects found and how they were retested, and points to the tool-generated evidence. No separate application was built for this assessment; every test targets the same integrated SE3090 system.

[15] p
1.2 System under test

[16] tbl
Layer
Technology and role
Backend
ASP.NET Core 8 Web API (Clean Architecture: Controllers, Services, Repositories, DTOs), JWT HMAC-SHA256, BCrypt (12 rounds), RFC 7807 error handling
Database
PostgreSQL 16 on Neon Cloud via Entity Framework Core 8 (Code-First). 11 tables in 3NF; unique constraint on Appointments(LawyerId, AppointmentDate)
Web client
React 19, Vite, TypeScript, TailwindCSS v4, React Router 7, Axios with auth interceptor, ProtectedRoute
Mobile client
Flutter 3.x, ChangeNotifier state, flutter_secure_storage, date/file pickers
Agentic AI
Python 3.11 FastAPI services (:8001 scheduling/documents, :8002 lawyer recommendation), Google Gemini 1.5/2.0 Flash, Pydantic I/O, human approval gate. Called only through the .NET API
Pipeline
GitHub Actions: backend.yml, frontend.yml, mobile.yml

7. Non-Functional Test Analysis

[145] p
7.1 Performance

[146] p
All transactional endpoints meet the NFR-01 target of p95 below 200 ms, and the AI recommendation endpoint meets the 1.5 s budget (p95 1,450 ms). The directory query is the fastest (p95 42 ms) and the AI call the slowest, as expected because it depends on an external LLM.

[147] p
Login is the closest transactional endpoint to the limit (p95 180 ms), because BCrypt with 12 rounds is deliberately slow. This is a security trade-off and is recorded as DEF-07 for monitoring.

[148] p
The AI endpoint has only about 50 ms of headroom (1,450 ms vs 1,500 ms) and a low throughput of 35 rps. Caching of repeated queries and a fallback ranking would protect the target.

[149] p
Atomic booking sustains 280 rps at p95 68 ms, supporting the zero-double-booking claim under load.

[150] p
7.2 Security

[151] p
Authentication, authorisation, password storage and prompt-injection defences were each tested with at least one negative case. The ZAP baseline scan, SQL-injection probe and upload-restriction tests are planned to complete the OWASP API Top 10 view.

[152] p
7.3 Reliability and recovery

[153] p
The architecture isolates the Python AI mesh from the transactional API (ADR-005). The failure-recovery case TC-C113 verifies that a Gemini timeout produces a safe error without affecting booking or database state.

[154] p
7.4 Usability and compatibility

[155] p
Web and mobile clients were verified against the same API with equivalent validation (TC-FE-02 and TC-MOB-03). A Lighthouse and axe accessibility run on the React app is recommended as an extension.
